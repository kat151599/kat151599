PROJECT CASE STUDY / Monitoring & reliability

VengMonitor — Industrial Monitoring

A read-only modernization layer for an existing ventilation system: status, history, persistent alarm events and notifications.

Used in an operational workflowPortfolio case study
ARCHITECTURE / DESIGN RATIONALE

Why a separate Mirror node?

The equipment network should keep monitoring independently of the internet and should not accept public control commands. Local alarm decisions and remote delivery are therefore deliberately separated.

01 · Existing systemVengSystem

Controls ventilation and writes measurement logs.

Read-only logs
→Local logs
02 · Local layerVengMonitor SERV

Parses measurements, stores history, sounds a local alarm and records raised / cleared transitions.

Alarm source of truth
→Outbound tunnel / API
03 · Remote layerVengMonitor Mirror

Protected connection, remote viewing, health monitoring and deduplicated event forwarding.

Own connectivity-loss alarm
→Views / notifications
04 · ConsumersWeb + Telegram

Remote status access and notifications about events already determined by SERV.

No ventilation control
01Local autonomy

SERV continues reading logs and sounding local alarms if internet access fails.

02Reduced exposure

Mirror separates remote access from the equipment-side network. The monitoring layer does not change control parameters.

03Reliable delivery

SERV records alarm start and end; Mirror forwards identified events without sending duplicates.

Connectivity loss is a separate Mirror event. The production architecture uses a 300-second sustained-loss threshold; the public demo intentionally accelerates this to 5 seconds.

The problem

The legacy controller managed ventilation, but the site needed remote visibility and actionable alerts without introducing changes to equipment control.

The solution

A local agent reads VengSystem logs, normalizes measurements and evaluates alarms. A separate Mirror component provides remote access and notification delivery.

Implemented features

  • Room-level temperatures and ventilation values with historical measurements.
  • Threshold, zero-ventilation, missing-data and stale-log detection.
  • Persisted alarm start/end transitions (raised / cleared).
  • Local sound and Telegram alerts with event deduplication.

Technical approach

Python · Flask · JavaScript · legacy log parsing · SERV/Mirror · Telegram. SERV remains the source of truth for alarms; local monitoring does not require internet access.

Demonstration & validation

The interactive demo above simulates fictional rooms, measurements and incident scenarios. The operational project was validated against incomplete log entries, network interruptions and false alarms. The public simulator is intentionally simplified and independent from production code.

Scope & privacy

The tool does not modify ventilation-control parameters. Site configurations and production code remain private.
